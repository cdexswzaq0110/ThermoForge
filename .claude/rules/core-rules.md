# 核心規則

只放所有任務都必須遵守、跨技術棧仍成立的規則。方法論、格式、清單與領域知識屬於 Skills，不在這裡重複。

**其他檔案以「第 N 條」引用本檔，編號必須穩定。**

## 1. 來源優先，假設透明

- 先讀取使用者指定的來源、現有程式碼、測試與專案文件，再提出方案或修改。
- 不以 AI 推論覆蓋已核准的需求或決策；來源衝突時指出衝突並確認權威來源。
- 無法由證據確認的內容，依 [`evidence-grades.md`](evidence-grades.md) 標記等級，不得寫成既成事實。

## 2. 保持可追溯

- 需求、驗收、設計、實作、測試與證據之間用穩定 ID 關聯，不靠標題或顯示群組猜測。
- 從外部來源匯入時保留來源檔、位置與原始 ID；衍生文件不得抹除來源。
- 區分需求／文件狀態、程式碼現況與驗證證據；計畫不等於完成。

## 3. 保護使用者工作與敏感資訊

- 保留既有變更，不覆寫、不刪除、不還原不屬於當前任務的工作。
- 破壞性、不可逆或會影響外部系統的動作屬 **Critical Section**：先確認精確範圍與授權，先打 backup tag，同時只能有一個持有者。
- 不提交秘密、憑證、個資或敏感營運資料；發現疑似曝露時停止擴散並清楚回報。
- **部分結果不覆蓋完整結果**：一次執行若因中斷或失敗而不完整，不得用它覆寫既有的完整產出。說明失敗、修好再跑。

## 4. 以證據宣告完成

- 依變更風險執行最接近實際行為的驗證；**不得把未執行的檢查描述為通過**。
- 回報實際執行的指令、結果、未驗證項目與殘餘風險。
- 驗收標準、測試與證據對不上時，狀態保持未完成或受阻。
- 派發紀錄如實填寫實際 Agent／模型／推理強度；取不到就寫 `unknown`，不得把預期值當執行證據。

## 5. 最小必要變更

- 寫程式前先爬最小實作階梯（`skills/se-minimal-change`）：不用寫 > 已經有 > 標準庫 > 平台原生 > 已裝依賴 > 一行 > 最小可動。
- 優先沿用專案既有架構、慣例與工具；避免與目標無關的重構或新依賴。
- 文件深度依風險與交付階段調整，不為了填滿模板而製造內容。
- 只有需要隔離權限、獨立 context、平行探索或第二意見時才派 Thread／Process（`dispatch.md`）。

## 6. 每一輪留下可檢索的領悟

一輪工作結束時，判斷有沒有**下一輪會再用到、而且這次是撞出來才知道的**東西。有就寫進 `docs/lessons/`（`skills/se-epiphany`）。

不寫的情況也要是判斷過的結果，不是忘記。這條是這套配置 存在的理由，不是加分項。
