# System Design — 九階段流程

**這是可執行的流程，不是知識清單。** 每一步都有輸入、動作、產出、卡住時怎麼辦。

適用：拿到 PRD 要寫架構文件 · 系統設計面試（45–60 分鐘） · 評估既有系統的瓶頸。

## 三種最常見的失敗

| 失敗模式 | 症狀 | 這套流程怎麼擋 |
|---|---|---|
| **直接畫架構圖** | 還沒估算就開始擺 Redis、Kafka | Stage 2 強制先量化 |
| **平均用力** | 每個元件都講一點，沒有一個講深 | Stage 6 強制挑 2–3 個瓶頸深挖 |
| **只講好處** | 「用 cache 就快了」，不講它引入什麼 | 每個 Stage 的產出都要求寫出取捨 |

## 七條鐵律

```
1. 先估數字，再選架構
2. 先找瓶頸，再加元件
3. 不同 path 有不同保證
4. 把不能錯的同步路徑縮到最小
5. 平均值會騙人 —— 看 p95/p99、per-key、per-shard
6. 每加一層，說出它引入什麼新故障模式
7. 能用 index + query 解決的，不要先加 Redis
```

## 九個階段

```
S0 需求預處理   → 名詞 / 動詞 / 數字 / 紅線 四張清單
S1 範圍收斂     → FR（3–5 條）+ 明確的 Out of Scope
S2 量化         → 五步估算 → 「第一個瓶頸假設」一句話
S3 實體與資料   → Entity → 不變量 → 狀態機
S4 API 契約     → 九項 Checklist 掃過
S5 High-Level   → 一條 request 的完整旅程，先能跑
S6 瓶頸深挖     → 挑 2–3 個，五段結構      ← 分數所在
S7 資料層決策   → 存哪 / 怎麼分 / 怎麼複製 / 怎麼一致
S8 韌性可觀測   → 檢查表跑一遍
S9 Review 交付  → 取捨總表 + 風險 + 不涵蓋
```

**時間分配**

| 情境 | S0–S1 | S2 | S3–S4 | S5 | S6–S7 | S8 | S9 |
|---|---|---|---|---|---|---|---|
| 45 分鐘 | 5 | 3 | 7 | 10 | 15 | 3 | 2 |
| 60 分鐘 | 6 | 4 | 8 | 12 | 20 | 6 | 4 |
| 真實工作 | 半天 | 半天 | 1 天 | 1 天 | 2–3 天 | 1 天 | 半天 |

> ⚠️ **最常見的時間分配錯誤**：High-Level Design 畫太久，Deep Dive 沒時間。
> **High-Level Design 只要「能跑」就往下走。**

## Stage 0 — 需求預處理

把文件讀成四張清單：

| 清單 | 抽什麼 | 變成什麼 |
|---|---|---|
| **名詞** | 反覆被提到的名詞 | 候選 Entity |
| **動詞** | 「使用者可以 ___」的句子 | 候選 API；**會改變世界狀態的就是 critical write path** |
| **數字** | 使用者數、QPS、延遲要求、保留期限、檔案大小 | Stage 2 的估算輸入；沒寫的標 `?` |
| **紅線** | 「不可以…」「必須…」「絕對不能…」 | **後面所有設計決策的最高優先級** |

紅線範例：不可 double booking · 不得產生幻覺 · 訊息不可遺失 · 同一台車不能同時接兩單。

**卡住時**：文件太長 → 只讀「使用者故事」與「驗收條件」兩節。文件太短 → 直接跳 Stage 1，把缺的列成問題。

---

## Stage 1 — 範圍收斂

### FR 寫 3–5 條，不要多

格式：`使用者應該能夠 <動詞> <名詞>，<約束>`

- ✅ 使用者可以依 location（城市名）與 dates 搜尋 listings
- ❌ 系統要支援搜尋功能

超過 5 條一定講不完，反而顯得沒有判斷力。真實工作可以多，但要標 P0／P1／P2。

### 明確寫下 Out of Scope（最常被跳過，但最重要）

價值有三：對方知道你有判斷力 · 避免自己越畫越大收不回來 · 真實工作中保護排程。

### 只問會改變設計的問題

四類必問：**規模**（DAU、讀寫比、尖峰倍數、保留多久）· **一致性**（哪些操作絕對不能錯、可接受幾秒舊資料）· **延遲**（user-facing path 的 budget、p95 還是 p99）· **邊界**（跟現有系統的關係、可以改嗎、要向後相容嗎）。

不要問：要支援手機嗎（假設要）· 用什麼語言（無關）· 預算多少（除非題目是成本優化）。

**帶著假設去問，不要空手問**：
❌「請問 DAU 多少？」
✅「我假設 DAU 是 1000 萬，如果超過 5000 萬我會需要重新評估分片策略，請確認。」

> 這是 `rules/dispatch.md` 第 4 條 GIL 的落地：一次只鎖住人最少的時間。

---

## Stage 2 — 量化（五步估算）

**這一步的產出不是一堆數字，而是一句話：「這個系統的第一個瓶頸最可能在 ___」。**

```
Step 1 估 request rate   平均 QPS = DAU × 每人每天次數 ÷ 86,400；尖峰 = 平均 × 10
Step 2 估資料量          row count × 單筆大小 × retention（再加 index 放大與副本）
Step 3 估 latency budget 把 end-to-end 拆開：網路 / Gateway / App / Cache / DB / buffer
Step 4 判斷第一個瓶頸    查下表
Step 5 才決定擴展手段    查下表
```

**Step 4–5 的兩張查表**（系統形狀 → 第一個瓶頸；症狀 → 先想什麼、不要太早跳到什麼）見 [`references/estimation-tables.md`](references/estimation-tables.md)。

**產出必須有這三行**：平均／尖峰 QPS 與讀寫比 · 資料量與總量 · latency budget 拆解 —— 然後是那句「第一個瓶頸假設」。

**卡住時**：完全沒數字 → 用量級替代。內部工具（幾千 DAU）→ 單一 PostgreSQL 就夠；消費級（千萬 DAU）→ cache + read replica；平台級（億級）→ sharding + 分區。

---

## Stage 3–5 — 實體、API、High-Level

**細節見 [`references/stages-3-5.md`](references/stages-3-5.md)。** 三件不能省的：

- **每個 Entity 寫出不變量**（`<在什麼範圍內>，<什麼條件>必須永遠成立`）——這一步決定後面的一致性設計。
- **九項 API Checklist 掃過一遍**；長任務一定用 202 模式。
- **每個元件標註「引入什麼新問題」**——這一欄是資深與初級的分野。

High-Level Design **只要能跑就往下走**，不要在這裡追求完美。

---

## Stage 6 — 瓶頸深挖 ← 分數所在

**挑 2–3 個，講深。不要每個都講一點。** 題目從 Stage 2 的「第一個瓶頸假設」來。

**症狀 → 模式對照表**與**三組可直接套的 Deep Dive 組合**見 [`references/deep-dive-patterns.md`](references/deep-dive-patterns.md)。

### 每個 Deep Dive 用同一個五段結構

```markdown
### Deep Dive N：<問題的一句話描述>

**問題**       具體失敗場景，最好帶數字或時間線
**方案比較**   | 方案 | 做法 | 優點 | 缺點 | 適合 |
**選擇與理由** 我選 ___，因為 ___
**代價**       這個選擇引入了 ___，我用 ___ 緩解
**怎麼驗證**   監控 ___ 指標；如果 ___ 超過 ___ 就代表方案失效
```

> **方案比較一定要有一個「不佳」的選項並說明為什麼不佳**——這證明你真的比較過，不是背答案。

---

## Stage 7 — 資料層決策

**細節見 [`references/data-layer.md`](references/data-layer.md)。** 四個問題必須全部回答：存哪裡 · 怎麼分 · 怎麼複製 · 怎麼一致。

兩條最容易錯的：

- **先問「真的需要 shard 嗎」。** 資料量 < 幾 TB、QPS 幾千 → 先調 index／cache／read replica。
- **把系統拆成 path，逐一決定一致性**（鐵律第 3 條）。Booking 走 CP，Browse 走 AP，不要整個系統套同一個保證。

產出必含 **Invariant → 保護機制對照表**。

---

## Stage 8 — 韌性與可觀測性

檢查表跑一遍就好，不需要每項深入。完整清單見 [`references/resilience-checklist.md`](references/resilience-checklist.md)。

四個必答：

- 哪些操作會競爭同一份狀態？用什麼保護？
- 過載時先丟什麼？（重試請求 → 低優先級 → 非核心）
- 每個外部呼叫都有 timeout 嗎？值怎麼定的？（下游 P99 的 2–3 倍）
- 會改變狀態的操作有 idempotency key 嗎？

**對症狀警告，不對原因警告**：❌ CPU > 80%　✅ 錯誤率 > 1%／P99 > 1 秒。

---

## Stage 9 — Review 與交付

交付文件固定十節，**第 9 節「取捨總表」是文件的價值所在**：

| 決策 | 選擇 | 放棄了什麼 | 什麼情況下要重新評估 |
|---|---|---|---|

完整文件結構見 [`references/deliverable-template.md`](references/deliverable-template.md)。

### 交付前自問

```
□ 每個 FR 都有對應的流程嗎？
□ 每條 Invariant 都有對應的保護機制嗎？
□ 每個新增元件都寫了「解決什麼」和「引入什麼」嗎？
□ Deep Dive 有比較過至少 2 個方案並說明為什麼不選另一個嗎？
□ 有沒有過度設計？（能用 index + query 解決的，硬加了 Redis 嗎）
□ 有沒有欠設計？（S2 判斷的第一個瓶頸，處理了嗎）
□ 明確寫出「這一版不涵蓋什麼」了嗎？
□ 有沒有把 secrets／API key／個資寫進文件？
```

## 與其他能力的關係

- 需求本身還模糊 → 先 `se-clarify` 設計樹模式，再回來走 Stage 0。
- 這個系統做不做得出來、划不划算 → `se-feasibility`。
- 設計定案後要拆成可執行的 Process → `se-design` 定接縫 → `se-scheduling` 派發。
- 每個結論帶證據等級（`rules/evidence-grades.md`）：估算是**推論**，實測數字才是**已確認**。

## 完成條件

- 四張清單（名詞／動詞／數字／紅線）已產出。
- FR 3–5 條，Out of Scope 已明確寫下。
- 「第一個瓶頸假設」寫成了一句話。
- 每條 Invariant 對應到一個具體保護機制。
- 挑了 2–3 個 Deep Dive，每個五段完整，且至少比較過兩個方案。
- 每個元件都寫了「引入什麼新問題」。
- 取捨總表與「不涵蓋什麼」已寫。
