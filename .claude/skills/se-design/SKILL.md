# Design — 探索到切片

**這條路不能中斷。** 探索 → 定接縫 → 切片，三步互為前提。中途 compact，後面每一片都會建立在摘要過的推導上。逼近 ~120k 就寫進計畫檔、開新 Process。

---

## Phase 1 — 探索意圖

不是「他要什麼功能」，是「**做完長什麼樣**」。

1. **先讀，再問。** 既有程式碼、測試、`CONTEXT.md`、相關 ADR。能自己查的事實自己查。
2. 講不清楚 → 載入 `se-clarify` 設計樹模式。
3. 不確定值不值得做 → 載入 `se-feasibility`。
4. 太大到連要問什麼都不確定 → 停下來，交棒 `se-discovery`。

**Phase 1 的產出是一句話**：做完之後，使用者能觀察到什麼變化。寫不出這句話就不要往下走。

---

## Phase 2 — 定接縫

**這一步最常被跳過，而它決定後面順不順。**

### 詞彙（用詞要精確，換詞就把歧義換回來了）

| 詞 | 意思 | 避免 |
|---|---|---|
| **Module** | 任何有介面與實作的東西。刻意不綁尺度：函式、class、package、跨層切片都算 | unit、component、service |
| **Interface** | 呼叫者為了正確使用它必須知道的**全部**——型別簽章，也包含不變式、順序約束、錯誤模式、必要設定、效能特性 | API、signature（太窄，只到型別層） |
| **Depth** | 介面上的槓桿——呼叫者或測試每學一單位介面，能操作到多少行為 | |
| **Seam** | 可以在不編輯該處的情況下改變行為的地方；模組介面**所在的位置**。放哪是獨立的決定，與後面放什麼分開 | boundary（與 DDD 的 bounded context 撞名） |
| **Adapter** | 在接縫上滿足介面的具體物。描述**角色**（填哪個槽），不描述內容 | |
| **Leverage** | 深度給呼叫者的：每學一單位介面得到更多能力 | |
| **Locality** | 深度給維護者的：改動、bug、知識、驗證集中在一處 | |

**深** = 小介面、大實作。**淺** = 介面複雜度接近實作。淺是要避免的那個。

### 三條原則

**深度是介面的性質，不是實作的性質。** 一個深模組內部可以由許多小而可換的零件組成——它們只是不屬於它的介面。

**刪除測試。** 想像把這個模組刪掉：複雜度消失了 → 它是 pass-through；複雜度在 N 個呼叫者身上重新出現 → 它在賺錢。

**一個 adapter 是假接縫，兩個才是真的。** 沒有東西真的在跨它變化就不要開——單一實作的接縫是投機的通用性穿了架構的外衣。

### 接縫選擇（四條，依序）

1. **沿用既有接縫**優於開新的。新接縫是新的介面表面，要學、要維護、要保持誠實。
2. **用能觀測到該行為的最高接縫。** 在還看得見結果的最外層介面測試，每個測試的槓桿最大，也最耐重構。
3. **越少越好，理想是一個。** 每個接縫既是可觀測點，也是可漂移點。
4. 真的需要新接縫 → **提在你能提的最高點**，並說出什麼東西跨它變化。

### 為可測試性設計

- **接受依賴，不要自己造。** `processOrder(order, gateway)` 可測；內部 `new StripeGateway()` 的不行。
- **回傳結果，不要製造副作用。** `calculateDiscount(cart): Discount` 可測；`applyDiscount(cart): void` 不行。
- **表面積要小。** 方法少 → 測試少；參數少 → setup 簡單。

### **接縫必須先跟人確認，才能寫第一個測試**

測試的力氣只有在接縫先談好時才會落在關鍵路徑上。**沒確認的接縫產出的是沒人要的測試。**

## Phase 3 — 切片

**縱切，穿過所有層。** 不要橫切（先做完 schema 層再做 API 層）——橫切的每一層都不能獨立驗證。

四判準（`se-scheduling` 也用同一組）：

1. **完整** — 端到端可觀察的結果
2. **可獨立驗證** — 有可重現的驗收條件
3. **塞得進一個新 Process** — 從零 context 開始還做得完
4. **接縫已定** — Phase 2 已確認

### 爆炸半徑大的變更

改共用型別、改公開介面、改 schema——**不要硬塞成一片**：

```
expand（新舊並存，加不刪） → migrate（分批搬呼叫端） → contract（刪舊的）
```

三個階段各自是一片，各自可獨立驗證、可獨立回滾。

### prefactor 排最前

要先整理才好動的部分，切成獨立的第一片，**不夾在功能片裡面**。夾進去會讓 review 分不出哪些改動是功能、哪些是整理。

---

## 交棒

Phase 3 完成 → 交給 `se-scheduling` 建 Ready Queue 與寫入鎖，然後每片開新 Process。

**規劃 Process 不實作。** 這是 context 邊界，不是儀式。

## 完成條件

- 「做完長什麼樣」有一句可觀察的描述。
- 接縫已選定並**經人確認**，選擇理由可追溯到四條規則。
- 切片全部通過四判準，`Depends on` 只含真依賴。
- 爆炸半徑大的變更已拆成 expand／migrate／contract。
- 本 Process 沒有開始實作。
