# Debug — 除錯迴圈

**沒有可重現的失敗就不要改 code。** 猜著改會產生兩個結果：碰巧好了（你不知道為什麼，所以它會回來），或沒好（你現在有兩個變數了）。

## 迴圈

```
1. 紅   — 做出一個會為這個 bug 失敗的迴圈
2. 縮   — 把它最小化到只剩必要條件
3. 猜   — 提一個可證偽的假設
4. 測   — 加儀器去區辨這個假設的真偽
5. 修   — 修根因，不修症狀
6. 綠   — 迴圈變綠，且回歸測試留下來
```

**每一階做完才進下一階。** 跳過第 1 階是最常見也最貴的錯誤。

---

### 1. 紅

做出一個**每次都會失敗**的東西：一個測試、一個腳本、一串指令。

「迴圈是紅的」是一個**二元的可觀察狀態**——它為這個 bug 失敗，或者沒有。這比「我大概重現了」精確，而精確在這裡就是全部。

做不出紅 → 你還不知道 bug 是什麼。回去收集：什麼輸入、什麼環境、什麼版本、什麼時候開始的。

間歇性失敗 → 先找出讓它穩定失敗的條件（順序、並行度、時間、資料量）。找不到就先把重現率量出來（20 次跑幾次紅）。

### 2. 縮

一次拿掉一個東西，保持紅。

拿掉之後變綠 → **那個東西是必要條件**，放回去，記下來。

縮到最後剩下的就是這個 bug 的**充要條件**。這一步做完，通常假設已經自己浮出來了。

### 3. 猜

寫下**一個**可證偽的假設：

```
假設：<機制>。
如果為真，<某個可觀察的東西>會是 <某個值>。
如果為假，它會是 <另一個值>。
```

**沒有區辨力的假設不算假設**（「大概是快取的問題」）。

### 4. 測

加儀器去看那個可觀察的東西：log、斷點、`print`、時間戳、狀態 dump。

**先看，再改。** 這一階的產出是一個事實【已確認】，不是一份修改。

假設被推翻 → 回第 3 階，寫下一個。**推翻的假設要記下來**——它是 `dead_end` 型的 Lesson 材料。

### 5. 修

**修根因，不修症狀。**

一份回報命名的是症狀。grep 你要動的那個函式的**每一個呼叫者**：在共用函式修一次，比每個呼叫端各補一次的 diff 更小；只補 Process 上寫的那條路徑，會留下一個還壞著的手足呼叫者。

修完問一次：**這個 bug 屬於哪一族？** 同一個錯誤假設會生出一整族的坑。

### 6. 綠

- 原本的紅迴圈變綠。
- **回歸測試留下來**——放在 `se-design` 確認過的接縫上，不是隨手找個地方。
- 一個「不會因為這個 bug 而紅」的回歸測試等於沒有（見 `se-two-axis-review` 的 Test That Cannot Fail）。

---

## 三次規則

**同一個 bug 修到第三次 → 停止改 code。**

不是繼續試，是：

1. 講出你一直在假設、但可能是錯的那件事。
2. 問一個診斷問題（給人，或給自己）。
3. **寫一則 Lesson**（`se-epiphany`）——修三次的東西，第四次一定還會來。

## 反模式

| 不要 | 因為 |
|---|---|
| 有猜測就先改，邊改邊看 | 每改一次就多一個變數 |
| 同時改兩個地方 | 好了也不知道是哪個 |
| 加一個 `try/catch` 讓錯誤不見 | 那不是修好，是把爆炸點搬到更遠的地方 |
| 加 `sleep` 讓 flaky 測試變綠 | 條件式等待，不是時間式等待 |
| 只修 Process 上寫的那條路徑 | 手足呼叫者還壞著 |
| 沒留回歸測試就宣告完成 | 它會回來，而且下次沒人記得 |

## 完成條件

- 有一個**曾經為這個 bug 變紅**的迴圈，且現在是綠的。
- 根因已命名，且已檢查同一個共用函式的其他呼叫者。
- 回歸測試留在已確認的接縫上。
- 走了三次規則的，已寫 Lesson。
