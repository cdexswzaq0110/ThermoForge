# Wayfind — 撥霧

**這是最重的流程。握得住的功能走 `se-design` 就好。**

判準只有一條：**你講不講得出「做完長什麼樣」？** 講得出來就不要用這個。

**只產決策，不產交付物。** 這裡不寫程式、不寫規格。

## 地圖

一份 markdown，住在 repo 裡（`docs/maps/<主題>.md`），**不住在 context 裡**。

```markdown
# 地圖：<主題>

## 終點
<一句話：這件事做完之後，世界有什麼不同。可以很模糊，但必須指向一個方向。>

## 已知
| 事實 | 證據等級 | 來源 |
|---|---|---|

## 決策節點

| # | 問題 | 型別 | 狀態 | 擋住誰 | 答案 |
|---|---|---|---|---|---|
| D1 | | 事實／取捨／可行性／範圍 | open／answered／dropped | D3, D4 | |

## 前緣
現在可以解的 Process：<清單>
```

### 四種 Process 型

| 型別 | 問的是 | 怎麼解 |
|---|---|---|
| **事實** | 世界是怎樣的 | 派 Thread 去查（程式碼、文件、網路） |
| **取捨** | 我們要選哪一個 | 攤開選項與代價，**交給人**（GIL） |
| **可行性** | 做不做得到 | `se-feasibility`，或做丟棄式原型 |
| **範圍** | 這算不算在裡面 | 交給人 |

## 流程

```
▸ Process 1  命名終點 → 廣度掃描 → 建立 Process → 連依賴 → 派 Thread Pool 查事實 Process → 停
▸ Process 2..N  一個 Process 解一個 → 寫答案 → 更新地圖 → 重算前緣
▸ 前緣穩定且終點講得出來了 → 交棒 se-design
```

### Process 1：不要一次做完

命名終點、掃一遍、把霧切成 Process、把能平行查的事實 Process 派出去——然後**停**。

不要在同一個 Process 裡開始解 Process。解 Process 的狀態要活在地圖裡。

### Process 2..N：一次一個

**一個 Process 只解一個 Process。**

解完寫答案回地圖，重算前緣，結束這個 Process。下一個開新的。

## 兩個最容易搞錯的

### 1. 把霧預先切成 ticket 大小

判準是「**現在能不能把問題講精準**」，不是「能不能回答」。

一個講得精準但答不出來的問題，是一個好 Process。
一個講不精準的問題，切多細都還是霧——它需要的是先解一個上游的 Process。

### 2. 一個 Process 想解好幾個

**狀態活在地圖裡，不活在 context 裡。** 一個 Process 解三個，第三個的品質會被前兩個的細節污染，而且下一個 Process 讀地圖時看不到那些推導。

## 出界訊號

**想直接動手的衝動 = 你已經走到地圖邊界了，該交棒**，不是可以加速。

其他訊號：

| 訊號 | 意義 |
|---|---|
| 前緣連續兩輪沒有變小 | Process 切錯了，或有一個上游 Process 沒被看見 |
| 一個 Process 解完沒有解鎖任何東西 | 它本來就不在關鍵路徑上，該 drop |
| 節點超過 30 張 | 終點定得太大。切成兩個地圖 |
| 開始想寫程式 | 交棒 `se-design` |

## 交棒

前緣穩定、終點講得出一句可觀察的話 → 交棒 `se-design`。

交棒時帶過去：終點那一句、已答決策節點的**答案**（不是過程）、還開著但已判定不擋路的 Process。

**地圖留在 repo**，不要刪。它是這件事為什麼長這樣的證據，也是 `se-epiphany` 的材料來源。

## 完成條件

- 地圖存在於 `docs/maps/`，且每個 Process 有型別、狀態與（已答的）答案。
- 事實 Process 的答案都帶證據等級與來源。
- 取捨 Process 與範圍 Process 都是**人**答的，不是 AI 猜的。
- 交棒時「做完長什麼樣」講得出一句可觀察的話。
