# Minimal Change — 最小實作階梯

**最好的程式碼是沒寫的那行。** 最小化的是**產出**，不是**理解**。

## 階梯

寫任何程式碼之前，停在**第一個成立**的階：

```
1. 這需要存在嗎？          → 不需要：跳過（YAGNI）
2. 這個 codebase 已經有？   → 沿用既有 helper／util／pattern，不要重寫
3. 標準庫做得到？          → 用它
4. 平台原生功能覆蓋？      → 用它
5. 已安裝的依賴解得掉？    → 用它
6. 能寫成一行？            → 寫成一行
7. 到這裡才：寫最小可動的  → 只寫任務需要的
```

**階梯在你理解問題之後才跑，不是取代理解。** 先讀任務、讀它會碰到的程式碼、追一次真實流程，然後才爬。

> 一個你不理解的小 diff 不是最小變更，是**第二個 bug 穿著效率的外衣**。

## Bug 修復 = 根因，不是症狀

一份回報命名的是**症狀**。

grep 你要動的那個函式的**每一個呼叫者**，在共用函式修一次——那裡加一道 guard，diff 比每個呼叫端各加一道小；只補 Process 上寫的那條路徑，會留下一個還壞著的手足呼叫者。

## 規則

- 沒有被明確要求的抽象，不要加。
- 能避免就不加新依賴。
- 沒人要的樣板不要寫。
- **刪除優於新增。無聊優於聰明。檔案越少越好。**
- 最短可動 diff 獲勝——但只在你理解問題之後。放錯位置的最小改動不是最小變更，是第二個 bug。
- 兩個標準庫做法長度一樣時，選**邊界案正確**的那個。目標是少寫程式，不是選比較脆的演算法。

## 五件不得省略的事

| 領域 | 為什麼 |
|---|---|
| **理解問題** | 讀完、追完真實流程，才選階 |
| **信任邊界的輸入驗證** | 外部進來的東西沒驗過就是洞 |
| **會造成資料遺失的錯誤處理** | 這類失敗沒有回頭路 |
| **安全** | 同上 |
| **無障礙** | 補回來的成本遠高於一開始就做 |
| **真實硬體需要的校準** | 平台從來不等於規格書：時鐘會漂、感測器會偏 |
| **任何被明確要求的東西** | 使用者要的就是範圍 |

**沒有檢查的最小實作是未完成的。** 非平凡的邏輯留下**一個可跑的檢查**——最小的、邏輯壞掉就會失敗的那個（一個 assert 式自測或一個小測試檔；不要框架、不要 fixture）。一行的瑣碎邏輯不需要測試。

## 刻意簡化要標記

真的切了一個角、而且有已知天花板（全域鎖、O(n²) 掃描、粗糙啟發式）時，留一行標記：

```python
# DEBT: 全表掃描，資料量 > 10k 會慢。升級：加索引或改增量比對
```

格式：`DEBT: <天花板>，升級：<觸發條件或路徑>`

**沒有升級路徑的標記會爛掉。** 定期用 `se-epiphany` 回顧時一併掃：

```bash
grep -rnE '(#|//|--) ?DEBT:' . --exclude-dir={node_modules,.git,dist,build}
```

輸出一行一則：`<檔案>:<行號>，<簡化了什麼>。天花板：<限制>。升級：<觸發>。`
沒寫升級觸發的標 `no-trigger`——那些是會靜靜腐爛的。
結尾：`<N> 個標記，其中 <M> 個沒有觸發條件。`

## 過度工程審查

審查一份 diff 時，一行一個發現：`<檔案>:L<行號>: <標籤> <什麼>。<用什麼取代>。`

| 標籤 | 抓什麼 | 取代成 |
|---|---|---|
| `delete:` | 死碼、用不到的彈性、投機功能 | 沒有 |
| `stdlib:` | 手刻了標準庫已有的東西 | 點名那個函式 |
| `native:` | 依賴或程式碼在做平台已經會的事 | 點名那個原生功能 |
| `yagni:` | 只有一個實作的抽象、沒人設定的 config、只有一個呼叫者的層 | 內聯回去 |
| `shrink:` | 同樣邏輯，更少行 | 寫出更短的形式 |

範例：

```
L12-38: stdlib: 27 行的驗證 class。email 有沒有 "@"，一行，真正的驗證是確認信。
L4:     native: 為了一次格式化引入 moment.js。Intl.DateTimeFormat，0 依賴。
repo.py:L88: yagni: AbstractRepository 只有一個實作。內聯回去，等第二個出現再說。
L52-71: delete: 對冪等的本地呼叫包了 retry。不需要取代物。
```

結尾只給一個數字：`net: -<N> 行可省。` 沒東西可砍就寫 `已達最小，出貨。` 然後停。

**範圍限定在過度工程。** 正確性 bug、安全漏洞、效能問題**明確在範圍外**——那些走 `se-two-axis-review`。一個 assert 式自測是本 skill 的最低標，**永遠不要把它列為可刪除**。

本 skill 只列出，不套用。要套用時明說。

## 一個接縫的判準

抽象值不值得存在，用刪除測試：

**想像把這個模組刪掉。** 複雜度消失了 → 它只是個 pass-through，刪。複雜度在 N 個呼叫者身上重新出現 → 它在賺錢，留。

**一個 adapter 代表假接縫，兩個才是真的。** 沒有東西真的在跨它變化，就不要開接縫——單一實作的接縫是投機的通用性穿了架構的外衣。
