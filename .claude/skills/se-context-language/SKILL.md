# Context Language — 共享語言

**`CONTEXT.md` 是這個專案的共享記憶體區段。** 所有 Process、所有 Thread、所有人，讀的是同一份定義。

## 為什麼值得

Agent 被丟進一個專案，被要求邊做邊猜行話，於是它用 20 個字講一件 1 個字就講得完的事：

- **之前**：「當一堂課程的某個章節裡的某一課被『實體化』（也就是在檔案系統上取得位置）時會有問題」
- **之後**：「materialization cascade 有問題」

省的不只是 token。連帶會發生的是：

- 變數、函式、檔案的**命名一致**，用的是同一組詞
- codebase 因此**更好導航**（對人與對 Agent 都是）
- Agent **思考時花的 token 更少**，因為它有一組更精簡的語言可用
- 需求討論與程式碼用同一組名詞，**L1 與 L3 之間的翻譯成本降到最低**（`rules/register.md`）

## 格式

`CONTEXT.md` 放在專案根目錄。四段，都不長。

```markdown
# <專案名> 共享語言

## Language

**<詞>**：
<一句話定義。用領域語言，不用實作細節。>
_避免_：<被這個詞取代掉的舊叫法>

## Relationships

- 一個 **A** 持有多個 **B**
- 一個 **B** 一次只帶一個 **C**
- **D** 是一種 **B**（附加了 X 條件）

## Flagged ambiguities

- 「<某詞>」曾同時指 <意思一> 與 <意思二> —— 已解決：<裁決結果>

## Out of scope

- <刻意不定義的詞，以及為什麼>
```

## 怎麼長出來

**不要一次寫完。** 一份 30 個詞的初版詞彙表，有 25 個是猜的。

長出來的三個時機：

| 時機 | 動作 |
|---|---|
| **命名衝突時** | 發現同一個東西有兩個叫法 → 當場裁決一個，寫進 Language，敗者寫進 _避免_ |
| **解釋超過兩句時** | 一個概念每次都要講三句才講得清 → 它值得一個名字 |
| **歧義被戳破時** | 發現一個詞在兩處指不同東西 → 拆成兩個詞，把過程寫進 Flagged ambiguities |

每次只加一到三個詞。**一個詞的定義寫不出來，代表這個概念本身還沒想清楚**——那是設計問題，不是文件問題。

## 挑詞的規則

1. **用領域已經在用的詞。** 業務方叫它什麼就叫什麼，不要發明工程術語再教他們。
2. **一個概念一個詞。** 同義詞不是豐富，是三個人各自理解一半。
3. **會被拿去命名程式碼的詞優先。** 詞彙表的價值兌現在 `class MaterializationCascade` 上。
4. **借用既有的概念**（既有的技術名詞、既有的比喻）比自創新詞便宜——自創的詞在模型的預訓練裡沒有先驗，你要花定義的 token 去買別人免費送的東西。
5. **不定義通用工程詞。** `cache`、`queue`、`retry` 不需要你的專案來定義。

## 維護

- **改動讓詞彙失真，就同一個 PR 一起改。** 過期的共享記憶體比不存在更貴——它會讓所有讀者的假設一起錯。
- 詞被淘汰時不要直接刪，移到 _避免_ 那一行。舊 commit、舊 issue、舊對話還在用它。
- 每次 `se-epiphany` 回顧時順手掃一次：有沒有詞已經沒人用了、有沒有新的行話還沒登記。

## 邊界

- 這個 skill 只管**建立與維護**詞彙表。
- 「讀 `CONTEXT.md` 拿詞彙」不需要這個 skill——那只是一行提示。
- 詞彙表不放需求、不放架構決策、不放待辦。那些各有各的家（規格、ADR、issue tracker）。
- 詞彙表不是縮寫表。`k8s` = `Kubernetes` 不值得一列。

## 完成條件

- `CONTEXT.md` 存在於專案根目錄，且被專案的 `CLAUDE.md` 指到。
- 每個詞有一句定義，被取代的舊叫法列在 _避免_。
- 曾經產生誤解的歧義都在 Flagged ambiguities 有裁決結果。
- 新增或裁決的詞，同一個 PR 內已同步到會用到它的程式碼命名。
