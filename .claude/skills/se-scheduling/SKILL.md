# Scheduling — 任務分解、執行派發、平行協調

執行模型的完整語彙在 [`../../EXECUTION_MODEL.md`](../../EXECUTION_MODEL.md)；常駐約束在 [`../../rules/dispatch.md`](../../rules/dispatch.md)。本檔是**操作程序**。

進入本 skill 時，你是 **Scheduler**。你擁有熱路徑：分解、派發、驗證、收斂。**你不做 Worker 級的工作，也不透過 Supervisor 執行。**

執行單元只有三層，沒有第四種：

```
Process   可獨立派發、獨立驗證的執行單元（完整 context 隔離）
  └─ Thread     Process 內可平行的更小單元（唯讀或無寫入衝突）
       └─ Coroutine  同 context 載入的方法（無隔離、無平行）
```

---

## Phase 0 — Frame（不可跳過）

在派任何東西出去之前，先講清楚三件事：

1. **交付物**是什麼。
2. **3 到 5 條可檢查的成功條件**。太模糊到寫不出來 → 問一個問題然後停，別開始派發。
3. **預算**：大約幾次派發、幾次外部查證。形狀參考：`子任務數 × 2 次派發 ＋ 5 次 Supervisor 諮詢`。

> 預算不是硬上限，是**超支不得靜默**的門檻。用完就停下來報告，讓人決定加碼或收斂。

同時做 **Connection 探測**（一次做完，不要邊跑邊發現）：哪些 CLI 在、哪些 MCP 活著、哪些 API key 有設、平台可用並行數多少。缺哪一個就當場說清楚怎麼補，並宣告會走哪條降級路徑。細節走 `se-preflight`。

## Phase 1 — 任務分解

把工作縱切成短小、完整、可獨立驗證的 **Process**。**縱切穿過所有層**，不要橫切（先做完 schema 層再做 API 層）——橫切的每一層都不能獨立驗證。

### 四判準

1. **完整** — 交付一個端到端可觀察的結果，不是只完成單一技術層。
2. **可獨立驗證** — 有能直接觀察或重現的驗收條件。
3. **裝得進一個新 Process** — 從零 context 開始，讀完該讀的還做得完。
4. **接縫已定** — 測試放哪已經確認過。

裝不進就往下拆；無法獨立驗證的就往上合併。

### Process 規格

完整模板見 [`templates/PROCESS_SPEC.md`](../../../templates/PROCESS_SPEC.md)。最小形式：

```markdown
# P<NN> — <標題>

- Depends on：無 ／ P<NN>
- Write lock：無 ／ <實際會寫入的檔案、模組、共用資源>
- 建議派發單位：Process ／ Thread ／ Coroutine

## 交付成果
從使用者或系統行為描述這個 Process 完成後實際成立的結果。

## 驗收條件
- 可觀察、可操作、可重現的判定方式。

## 內部 Thread（可省略）
這個 Process 內可平行的唯讀子工作。寫入範圍相交的不要列。
```

### 依賴最小化（最常做錯的一步）

**分解完成前必須最大化初始 Ready Processes。**

不得因為以下理由建立 `Depends on`：

- 編號或建議順序
- 共用唯讀程式碼
- 尚未查證的「可能會衝突」

只有**後一個確實需要前一個的產物或決策**時才是真依賴。

> **寫入衝突不是依賴，是 Mutex。**
> 兩個 Process 都要改 `src/auth/session.ts` → 標同一把鎖，讓排程器序列化它們，**不要串成 `Depends on` 鏈**。
> 差別在：**鎖只是不能同時跑，依賴是順序固定。** 錯標成依賴會憑空製造一條假的關鍵路徑。

### 什麼時候往下切成 Thread

一個 Process 內部，**不寫入工作樹**或**寫入範圍互不相交**的子工作可以並行成 Thread：

| 適合 Thread | 不適合（留在 Process 內序列做） |
|---|---|
| 廣度搜尋、定位 | 任何會寫工作樹且範圍相交的 |
| 多軸審查（Spec／Standards） | 需要看到前一步結果才能開始的 |
| 多來源查證 | 會動 Schema、Migration、Lockfile 的 |

### 驗收條件的最低標

- 「完成實作」不是驗收條件，那只是在宣稱做完。
- 「測試通過」可以作為**證據**，但不能取代功能本身應達成的結果。
- 有使用者介面的，驗收條件必須包含實際操作流程，不能只有 API 回應。

## Phase 2 — 建 Ready Queue

```
Ready Queue = { Process | Depends on 全數完成 ∧ 所需鎖全部可取得 }
```

派發規則：

- **Ready 的全部立即派發，用滿平台可用並行數。** 不自行保守限制。
- 少量修改重疊不必直接改成循序——只要能隔離工作，且有明確的合併、驗證與回復方式，就可以並行。
- 只有**真前置依賴、無法隔離的共享資料、Critical Section、平台硬性限制**才序列化。
- 每個 Process 完成、受阻或釋放寫入範圍後，**立即重算 Ready Queue** 並派出新解鎖的工作。

### 死結與飢餓

| 症狀 | 處置 |
|---|---|
| 兩個 Process 互相等對方的產物（deadlock） | 依賴標錯了，或分解切錯了。拆依賴或合併成一個 |
| 某個 Process 永遠被判定為衝突而排不到（starvation） | 它的寫入範圍太寬。拆小，或安排一段獨占時間窗 |
| Ready Queue 一直是空的 | 依賴鏈拉成了直線。回 Phase 1 重拆 |

## Phase 3 — 派發

### 選單位

```
需要隔離嗎？
├─ 不需要 ──────────────────────── Coroutine（載 skill，自己做）
└─ 需要
   ├─ 只讀，不寫工作樹 ──────────── Thread
   └─ 要寫工作樹或要換乾淨 context ─ Process
```

**首次派發前必讀** [`references/dispatch-contracts.md`](references/dispatch-contracts.md)：派發資料清單、Worker 契約全文、派發紀錄欄位、難度選模、升級階梯、降級模式。

三條在這裡就要記住的：

- 每次派發**前**記錄實際 Agent／CLI／模型／推理強度。取不到就記 `unknown`，**不得把預期值當成執行證據**（`core-rules` 第 4 條）。
- 寫入鎖是**邊界宣告**，不是檔案白名單。
- Reviewer **不依難度換模型**——難度路由是為了省成本，審查的成本省錯地方會讓整條流程的保證失效。

## Phase 4 — 驗證

**驗證必須碰到交付物本身。**

grep 一下 README、測一個相鄰的東西、印出 `True` 然後 exit 0、再確認一次檔案存在——**這些都證明不了任何事**。跑真正的指令，讀真正的輸出。

每個結果三選一：

| 判定 | 意義 | 動作 |
|---|---|---|
| **PASS** | 對照它自己的驗收條件成立，有可重現證據 | 釋放鎖，重算 Ready Queue |
| **FIX** | 沒成立 | **重新派發，指名具體失敗**。不得手動補丁一個實質失敗 |
| **ESCALATE** | 超出成功條件、或第二次驗證失敗 | 升級 Supervisor 或交給人 |

**不得默默接受部分通過。**

多個 Worker 結果衝突時：**顯式解決，不取平均。** 依證據優先序判斷 —

1. 可重現失敗，以及安全或資料風險
2. 核准的規格與驗收條件
3. ADR、正式標準與公開契約
4. 測試、型別與執行證據
5. 工程經驗與 code smell

個人偏好不能單獨成立結論。

---

## Phase 5 — 升級 Supervisor（承諾邊界）

Supervisor 是**最強推理模型的唯讀 Thread**（`agents/thread-supervisor`）。它做策略、分解批判、風險、品味。**它從不執行。**

四種情況才升級，其餘時候不進熱路徑：

1. 兩個 Worker 的結果互相矛盾，且超出已提供的 context
2. 同一個子任務驗證失敗兩次
3. 判斷落在成功條件之外
4. 計畫需要結構性改變

另有兩次**強制諮詢**：計畫定案前（分解批判）、交付物成形後（品味與風險）。
每次諮詢後說明：**改了什麼、駁回了什麼**。

---

## Phase 6 — 收斂

- **Barrier**：所有 Process PASS 之後，才對照原始需求做一次總驗收。逐個宣稱完成不等於整體成立。
- 有可操作介面的，實際開起來走一次主要流程；自動化測試與 API 呼叫只能是補充。做不到就直說做不到，**不宣稱通過**。
- 收尾走 `se-two-axis-review` → `se-branch-lifecycle` → `se-epiphany`。

## 狀態板

每個派發步驟後印一行，讓人不用問就知道現在在哪：

```
T2: FIX → PASS | claude→codex | 重試 1 次
P4: DISPATCHED | opus-5/high | 鎖: src/auth/**
P5: BLOCKED    | 等 P4 | 原因: 需要 P4 的 schema 決策
```

欄位：單位＋編號、狀態（PENDING／DISPATCHED／PASS／FIX／ESCALATED／BLOCKED）、實際派發路徑、重試次數、持有或等待的鎖。

## 完成條件

- 每個 Process 都有可判定的交付成果與驗收條件，且有可重現證據。
- 依賴只有真依賴；寫入衝突標成鎖不標成依賴。
- 所有派發都記錄了實際配置（取不到記 `unknown`）。
- 總驗收已對照原始需求跑過。
- 預算若超支，已停下來報告過。
