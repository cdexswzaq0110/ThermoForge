# Feasibility — 可行性評估

**先查證，再判定。** 不修改需求、架構或程式。

「成功」的定義：**在已確認的環境、成本與時間內達成目標結果。** 三個限定詞缺一，評估就沒有意義。

## 流程

1. **確認目標與成功定義。** 講不出「達成長什麼樣」→ 先回 `se-clarify`，不要硬評。
2. **查證**：技術能力、既有實作、外部依賴、權限、資料、硬體、**目前價格**。
3. **分項評估**：技術、架構相容、外部依賴、驗證方式、成本、時間、主要風險。
4. **依證據選一個機率區間**，不給假精確的百分比。
5. **產出報告**，然後問使用者：維持方案／縮小範圍／補驗證／停止。

**不得**自動接著開始規劃或實作。

價格或外部能力可能變動 → 查官方來源並**註明查證日期**。查不到就寫「不知道」，不要推估一個數字然後讓它變成事實。

## 分級

區間下限包含、上限不包含；100% 含在最後一級。

| 成功機率 | 圖示 | 判定 | 建議 |
|---|---|---|---|
| 0%–12.5% | 🔴 | 幾乎不可能 | 停止，或改用可行替代方案 |
| 12.5%–37.5% | 🟠 | 難度偏高 | 縮小範圍，或先驗證關鍵假設 |
| 37.5%–62.5% | 🟡 | 難度中間 | 列出優先驗證項目 |
| 62.5%–87.5% | 🟡🟢 | 成功機率偏高 | 列出主要剩餘風險 |
| 87.5%–100% | 🟢 | 成功機率非常高 | 列出主要剩餘風險 |
| 證據不足 | ⚪ | **無法評估** | 列出缺少的關鍵證據 |

**⚪ 不是逃避，是一個合法結論。** 核心依賴沒驗證過、或成功定義不清時，硬給一個數字比說「不知道」更糟——那個數字會被拿去做決定。

## 判定規則

- 百分比是**工程估計區間**，不是統計保證。報告裡要寫這句。
- 分別列出**支持證據、反對證據、假設、未知**。每一項帶證據等級。
- **不取各項平均。** 單一關鍵阻擋可以壓低整體上限——依賴拿不到就是 🔴，不管其他六項多好。
- 成本寫**金額區間**；沒有可靠價格時只寫低／中／高並說明原因。
- 時間寫**區間與前提**，並且**分開標示實作時間與外部等待時間**（審核、採購、對方回覆）。這兩個混在一起會讓人以為加人可以加快。
- 一定要給**最小降風險方法**：縮小範圍、做原型、先研究，或停止。

## 報告格式

```markdown
# 可行性評估：<名稱>

**結論：〈判定〉｜成功機率〈區間〉** 〈圖示〉

> 此區間是依目前證據做出的工程估計，不是統計保證。
> 查證日期：<YYYY-MM-DD>

## 成功定義
在 <環境> 下，於 <成本> 與 <時間> 內達成 <可觀察結果>。

## 評估

| 面向 | 結論 | 依據 | 證據等級 |
|---|---|---|---|
| 技術 | | | |
| 架構相容 | | | |
| 外部依賴 | | | |
| 驗證方式 | | | |
| 成本 | | | |
| 時間（實作／外部等待分列） | | | |

## 關鍵風險
單一關鍵阻擋排最前。

## 假設與未知
| 項目 | 是假設還是未知 | 錯了會怎樣 | 怎麼便宜地驗證 |
|---|---|---|---|

## 建議
繼續／縮小範圍／先驗證／停止 —— 以及**最小的下一步**。
```

## 完成條件

- 報告頂部有判定、區間與查證日期。
- 成本、時間、證據、假設、未知都已說明，且各帶證據等級。
- 沒有把猜測寫成精確機率。
- 時間有分開實作與外部等待。
- 沒有自動修改需求、架構、規格或程式。
