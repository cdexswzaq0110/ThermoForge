# 已拒絕的機制

維護契約第 5 條的落地處：**退役或否決一個機制時，在這裡留一檔**（概念、理由、先例）。重新提案前先讀它。

## 為什麼要有這個目錄

一個被拒絕過的想法會**反覆被重新提出**——尤其是那些聽起來很有道理的。沒有紀錄的話，每次都要重新論證一遍，而且有時候會論證出不同的結論。

這裡不是垃圾桶，是**決策的記憶**。

## 格式

`<機制名>.md`：

```markdown
# <機制名>

- **提案日期**：<YYYY-MM-DD>
- **拒絕日期**：<YYYY-MM-DD>
- **狀態**：已拒絕／已退役／條件性拒絕

## 概念
它是什麼、想解什麼問題。用提案者會認同的說法寫——**寫成稻草人就失去意義了**。

## 為什麼拒絕
具體理由。「感覺太複雜」不是理由；「它要求每次任務多花 N 步，而它解的問題在過去 M 輪出現 0 次」是。

## 先例
誰試過、結果如何。有的話附連結。

## 什麼情況下該重新考慮
具體、可觀察的條件。填不出來的話，這是**永久拒絕**而不是條件性拒絕，明說。
```

## 目前的紀錄

建立這套配置時明確不採用的機制，理由記在 [`../../docs/DESIGN_RATIONALE.md`](../../docs/DESIGN_RATIONALE.md) 的「刻意不做的事」一節。

**其中任何一項要重新提案，先讀那一節。** 之後每退役一個機制，在這個目錄新增一檔。
