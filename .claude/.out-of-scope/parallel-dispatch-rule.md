# 常駐規則：「平行 = 把多個派發放進同一則訊息」

- **提案日期**：2026-09-02
- **拒絕日期**：2026-09-02
- **狀態**：已拒絕（實測後撤回）

## 概念

`EXECUTION_MODEL.md` 與 `rules/dispatch.md` 第 3 條都要求「能平行就全部立即派發，用滿平台並行數」，但**沒有任何一處說明並行的機制是什麼**。

提案：在 `dispatch.md` 第 3 條補一句——平行的機制是把多個派發放進同一則訊息，分次送出就是序列化。並在 `se-two-axis-review` Phase 3 拿掉「並行數不足時依序派」這個沒有條件的免死金牌。

提案的觸發事件：實測雙軸 review 時，觀察到 `thread-reviewer-spec` 與 `thread-reviewer-standards` 被派在**不同的 assistant 訊息**裡，判定為違反「用滿並行數」。

## 為什麼拒絕

**兩個獨立的理由，任何一個都足以拒絕。**

### 一、當初的觀測值量不到那件事

headless `claude -p` 跨三次執行、99 則 assistant 訊息，**每一則都只含 1 個工具呼叫**，最大批次永遠是 1——不只 `Task`，`Read`／`Grep`／`Bash` 全部一樣【已確認：`docs/eval/run_eval.py --parse-only` 對三份 transcript 的 `max_batch`】。

那個環境根本不批次任何工具呼叫。「沒有並行」這個觀測值裡，被測系統的貢獻是零。

而且改完之後重測，行為**完全沒變**【已確認】——這是規則無效的直接證據，早於後來的儀器自檢發現。

### 二、不加規則也會發生

2026-09-02，在**已經撤回全部三個改動**的 working tree 上（`dispatch.md` 回到原狀），互動 session 一次從同一則訊息送出兩個 `Task` 呼叫，兩個 reviewer thread 同時啟動【已確認：本次對話即為實例】。

**沒有那條規則，行為照樣正確。** 依 `ABLATION.md` 的判準，一條加了不改變行為的常駐文字，只是每輪都在花 token。

### 附帶：拿掉免死金牌會讓文件說謊

`se-two-axis-review` Phase 3 的「並行數不足時依序派」，在 headless 環境下**是準確的描述**。刪掉它，文件就會要求一件那個環境做不到的事。

## 先例

同一輪裡的 `docs/lessons/0003` 第 4 個坑記錄了完整過程：一份「執行模型缺陷」報告、三個檔案的改動，全部建立在一個量不到的量測上。

## 什麼情況下該重新考慮

三個條件**同時**成立才重新提案：

1. headless CLI（或屆時的量測環境）支援單則訊息批次多個工具呼叫——否則一樣量不到；
2. 在那個能量測的環境裡，觀察到**該平行卻序列**的實例；
3. 該實例**反覆出現**，不是單次。

第 2 條沒有具體實例之前，這是永久拒絕。
