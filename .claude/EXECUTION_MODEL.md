# 執行模型（Execution Model）

**任務分解、執行派發、平行協調**——三件事全部用作業系統併發模型命名。

理由不是好聽：依賴關係、context 邊界、檔案寫入衝突、外部資源配額，本來就是排程與同步問題。借用既有語彙讓判斷有現成的直覺可用——**你已經知道兩個 thread 同時寫同一塊記憶體會出事。**

---

## 一、任務分解（Task Decomposition）

工作往下拆，只有三層。**一個可獨立派發的執行單元就叫 Process，更小的並行單元叫 Thread。**

```
Workload（一輪工作）
│
├─ Process ──────── 可獨立派發、獨立驗證的執行單元
│   │               完整 context 隔離，靠 IPC 訊息傳值
│   │
│   ├─ Thread ───── Process 內可平行的更小單元
│   │               獨立 context 視窗，共享工作樹，唯讀或無寫入衝突
│   │
│   └─ Coroutine ── 同一個 context 內載入的方法，無隔離、無平行
│
└─ Process ──────── （與上一個互不相依，或只共用寫入鎖）
```

### 分解判準

一個 **Process** 必須同時滿足四條，缺一就是切錯：

1. **完整** — 交付一個端到端可觀察的結果，不是只完成單一技術層。
2. **可獨立驗證** — 有能直接觀察或重現的驗收條件。「完成實作」不是驗收條件。
3. **裝得進一個新 Process** — 從零 context 開始，讀完該讀的還做得完。
4. **接縫已定** — 測試放哪已經確認過。

裝不進一個 Process = 切太粗，回去重切。
無法獨立驗證 = 切太細，往上合併。

一個 **Thread** 是 Process 內部**不寫入工作樹**、或**寫入範圍與其他 Thread 不相交**的子工作。典型：廣度搜尋、多軸審查、多來源查證。

一個 **Coroutine** 不是工作單元，是**方法**。載入一個 skill 就是 yield 進去，跑完 yield 回來。

### 依賴最小化

分解時**最大化初始 Ready Processes**。不得因為以下理由建立 `Depends on`：

- 編號或建議順序
- 共用唯讀程式碼
- 尚未查證的「可能會衝突」

只有**後一個確實需要前一個的產物或決策**時，才是真依賴。

> **寫入衝突不是依賴，是 Mutex。** 兩個 Process 都要改同一個檔案 → 標同一把鎖讓排程器序列化它們，不要串成 `Depends on` 鏈。
>
> 差別在：**鎖只是不能同時跑，依賴是順序固定。** 標錯會憑空製造一條假的關鍵路徑。

## 二、執行派發（Dispatch）

### 選單位

```
需要隔離嗎？
├─ 不需要 ──────────────────────── Coroutine（載入 skill，繼續在同一個 context 做）
└─ 需要
   ├─ 只讀，不寫工作樹 ──────────── Thread
   └─ 要寫工作樹或要換乾淨 context ─ Process
```

| 單位 | 隔離 | 平行 | 成本 | 什麼時候用 |
|---|---|---|---|---|
| **Coroutine** | 無（同 context） | 否 | 極低 | 需要一套**方法**，不需要隔離 |
| **Thread** | 獨立 context 視窗，共享工作樹 | 是 | 低 | 唯讀 fan-out：搜尋、審查、第二意見、蒐證 |
| **Process** | 完整（獨立 context、獨立歷史） | 是 | 高 | 一個垂直切片、規劃→實作的邊界 |
| **Connection** | 外部資源 | 受配額限制 | 依資源 | CLI、MCP server、瀏覽器 session、DB、API 配額、GPU |

**預設是 Coroutine。** Thread 與 Process 都有啟動成本（重建 context、重讀檔案、結果要再收斂一次），只有在隔離真的買到東西時才付。「分工看起來比較專業」不是隔離買到的東西。

### 三個角色

| 角色 | 是什麼 | 做什麼 | 不做什麼 |
|---|---|---|---|
| **Scheduler** | 主 Process | 分解、派發、驗證、收斂 | 不做 Worker 級的工作 |
| **Supervisor** | 最強推理配置的唯讀 Thread | 只在**承諾邊界**被諮詢：策略、分解批判、風險、品味 | **從不執行** |
| **Worker** | Thread Pool／Process Pool 成員 | 通過驗證的最便宜配置 | 不自我核准、不接下一個 Process |

**承諾邊界**——只有這四種情況升級到 Supervisor，其餘時候它不進熱路徑：

1. 兩個 Worker 的結果互相矛盾，且超出已提供的 context
2. 同一個子任務驗證失敗兩次
3. 判斷落在既定成功條件之外
4. 計畫需要結構性改變

另有兩次強制諮詢：計畫定案前（分解批判）、交付物成形後（品味與風險）。

> **模型是旋鈕，層級才是不變的部分。** 模型代號會換代，「Supervisor 用你能拿到最強的推理配置、Worker 用能通過驗證的最便宜配置」這條不會。

### 派發紀錄

每次派發**前**記錄：派發單位 · 角色 · 實際 Agent／CLI · 實際模型 · 實際推理強度 · 持有的鎖 · 難度判定依據。

取不到就如實記 `unknown`。**不得把預期值當成執行證據。**

## 三、平行協調（Parallel Coordination）

### Ready Queue

```
Ready Queue = { Process | Depends on 全數完成 ∧ 所需鎖全部可取得 }
```

- **Ready 的全部立即派發，用滿平台可用並行數。** 不自行保守限制。
- 每個 Process 完成、受阻或釋放寫入範圍後，**立即重算 Ready Queue**。
- 只有真前置依賴、無法隔離的共享資料、Critical Section、平台硬性限制才序列化。

### Pool

Pool 的意義是**有上限、可回收、不洩漏**。

| Pool | 成員 | 上限 | 回收 | 禁止 |
|---|---|---|---|---|
| **Thread Pool** | 唯讀 Subagent | 平台可用並行數，用滿 | 回報結構化結果後即結束，不留狀態 | 成員之間互讀對方結論（首輪必須獨立） |
| **Process Pool** | 獨立 Task | 能安全隔離的寫入範圍數量 | 結束時釋放所有寫入鎖並更新 Ready Queue | 兩個 Process 對同一分支做 git 寫操作 |
| **Connection Pool** | 外部資源 | 資源本身的配額 | 用完歸還 | 取得後不釋放（殭屍 session） |

### Connection Pool 的三條規則

外部資源不是無限的：AI CLI 有並行數與 rate limit · MCP server 有連線數與啟動成本 · 瀏覽器 session 有登入態 · DB／API 有連線上限 · GPU 一次一個。

1. **先探測再使用**——不只看命令存不存在，要真的跑得起來。
2. **記錄實際用到的是哪一個後端**——每種能力維護「首選 ▸ 備選」有序清單，換接入方式 = 調整清單順序，不是重寫流程。
3. **失敗時降級到備選並說明**——靜默降級最貴的地方不是效能，是**你以為你有的保證其實沒有**。

### 同步原語

| 原語 | 在這裡是什麼 | 違反的後果 |
|---|---|---|
| **Ready Queue** | `Depends on` 已全數完成的 Process 集合 | 沒重算就派發 → 做到一半發現前置沒好 |
| **Mutex（寫入鎖）** | 同一檔案／模組／Schema／Migration／Lockfile／同分支 git 寫入 | 覆蓋彼此的變更 |
| **Semaphore** | 平行上限：平台並行數、API rate limit、GPU 張數 | 429、逾時、被限流 |
| **Critical Section** | 不可逆操作：`push --force`、`reset --hard`、migration、部署、刪資料 | 沒有回頭路 |
| **Barrier** | 所有 Process 完成後才做的總驗收 | 逐個宣稱完成，整體其實不成立 |
| **Fork / Join** | 派發 → 收斂結論 | 只 fork 不 join：結果散落在各 Thread 的回報裡沒人整合 |
| **Race Condition** | 兩個 session 同時推進同一個 ref | 重複 cherry-pick、分支 tip 對不上 |
| **Deadlock** | 兩個 Process 互相等對方的產物 | 整條流程停住 → 拆依賴或合併 |
| **Starvation** | 某個 Process 永遠排不到（總是被判定為衝突） | 拆小它的寫入範圍 |
| **GIL** | **使用者本人**。需要人拍板的決策全域序列化 | 同時丟三個決策給人，等於三個都卡住 |

### GIL 這條要特別記

人的決策是全域鎖。**同一時間只該有一個問題在等人回答。**

- 能自己查的**事實**自己查（環境、程式碼、文件、工具）。
- 只把**決策**交給人，一次一個，附推薦答案與代價。
- 發現多個缺口時，只問「猜錯要重做」的那些（上限 3 個），其餘宣告假設往下走。

## 四、配置元件的對應

| 元件 | 執行模型對應 | 意義 |
|---|---|---|
| `rules/` | **Kernel** | 常駐、每個 Process 與 Thread 都繼承，不可停用 |
| `skills/` | **Coroutine 庫** | 同一個 context 內 yield 進去、跑完 yield 回來 |
| `agents/` | **Thread／Process 模板** | 建立時就決定隔離等級、工具權限與回收方式 |
| Task／新 session | **Process** | 獨立 context，不共享記憶體 |
| Subagent | **Thread** | 獨立 context 視窗，共享工作樹 |
| 交接文字 | **IPC 訊息** | Process 之間唯一合法的傳值方式，必須可序列化且自足 |
| `CONTEXT.md` | **共享記憶體區段** | 全體共用的命名與定義；改它等於改所有人的假設 |
| `docs/lessons/` | **持久化儲存** | 跨 Process 存活，Process 死了它還在 |
| Context window | **記憶體** | 有上限，會 OOM |
| Compact | **Swap** | 換出去再換回來會失真。能開新 Process 就不要 swap |

### 記憶體管理

| 概念 | 規則 |
|---|---|
| **水位線 ~120k** | 分解還沒完成就逼近它 → 寫進計畫檔、開新 Process。不要硬撐 |
| **OOM** | Context 爆掉。表現是模型開始忘記前面確認過的事 |
| **Swap（compact）** | 會失真。跨 Process 靠**落地產出**接續（計畫檔、測試、commit），不靠對話摘要 |
| **不可中斷區** | 探索 → 規劃 → 分解，全程同一個 Process。中途 swap，後面每個 Process 都建立在摘要過的推導上 |
| **必須中斷區** | Process 之間。上一個的實作細節對下一個是雜訊 |

## 五、升級與降級

| 情況 | 動作 |
|---|---|
| Worker 回報能力不足（**有可重現證據**） | 換更強配置的新 Worker 接手同一個 Process 與既有證據 |
| 已是最強配置仍受阻 | 依實際阻擋繼續查證，或交給 GIL（問人） |
| Thread 拿不到必要資料 | 回報阻擋，不猜測性擴大範圍 |
| Connection 首選失效 | 降級到備選，**明說換了哪一個**，不靜默切換 |
| 某個角色完全沒有可用路徑 | Scheduler 暫代，同樣預算，產出標記 `[降級: <角色>]` 並註明 context 隔離已失效。**最多涵蓋一個角色** |
