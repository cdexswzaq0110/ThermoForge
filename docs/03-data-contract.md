# 03 — 資料契約與切分（Gate 1）

> `se-ml-lifecycle` Stage 2。**這一階段錯了，後面任何分數都沒有意義。**
> 本檔記錄的兩個發現都是跑出來才知道的，不是設計時想到的。

## Schema

`data/processed/v1.npz`，4400 列，1100 個 base layout。

| 欄位 | 形狀 | 型別 | 意義 |
|---|---|---|---|
| `power_map` | (n, 64, 64) | f32 | 面功率密度 W/m² |
| `temperature` | (n, 64, 64) | f32 | 溫度場 °C（**target**） |
| `kt`, `h_conv`, `t_amb` | (n,) | f64 | 片導熱 W/K、對流係數 W/m²K、環境溫度 °C |
| `lx`, `ly`, `total_power` | (n,) | f64 | 板長寬 m、總功率 W |
| `theta_avg` | (n,) | f64 | 板面平均溫升 K（＝ P/(h·A)，精確） |
| `n_components` | (n,) | i64 | 元件數 |
| `base_id` | (n,) | i64 | **切分組別** |
| `regime_code` | (n,) | i8 | 0=id，1..5=五個 OOD regime |
| `fold` | (n,) | i64 | validation fold；**OOD 一律 −1** |
| `energy_residual` | (n,) | f64 | 生成時的守恆殘差 |

`fold = −1` 不只是標記。它讓「不小心把 OOD 拿去訓練」在索引層就成立不了——
`Dataset.id_only` 取的是 `fold >= 0`。這比寫一條「記得排除 OOD」的紀律可靠。

一列的真實世界含義：**一塊板子在一組固定的散熱條件下，達到穩態時的溫度分佈。**

## 取樣設計

分佈定義在程式碼（`thermoforge/data/sampler.py` 的 `ID_RANGES` 與 `OOD_REGIMES`），
不在 yaml。改一個 regime 的邊界會讓所有既有分數失去可比性，那種改動應該進 diff 被人看見。

| 參數 | ID 範圍 |
|---|---|
| 板長 Lx | 0.12 – 0.25 m |
| 長寬比 Lx/Ly | 0.80 – 1.25 |
| 片導熱 kt | 0.08 – 0.30 W/K |
| 對流係數 h | 15 – 80 W/m²K |
| 環境溫度 | 20 – 45 °C |
| 目標熱點溫升 | 15 – 90 K |
| 元件數 | 3 – 7 |
| 元件邊長 | 8 – 30 mm |

### 發現一：直接抽功率會生出 1087 °C 的板子

第一版各自獨立抽總功率與對流係數。跑出來的熱點溫度分佈是
中位數 104 °C、p99 314 °C、**最大 1087 °C**【已確認：2026-09-07 第一版 v1 的實測】。

沒有材料在 1087 °C 下還是一塊 PCB。而那些樣本會直接主導 field MAE——
模型會把容量花在一段不會出現在真實產品裡的分佈上，然後所有比較都被它們決定。

修法是改變**參數化**，不是過濾樣本：先抽目標熱點溫升，再用解析估計回推總功率。
估計式只用輸入（幾何、kt、h），不碰求解器輸出，所以這是在定義設計空間，
**不是**對 target 做篩選——後者會讓驗證集不再代表推論時會遇到的分佈。

修完的分佈：中位數 89.1 °C、p99 149.4 °C、最大 179.8 °C【已確認：現行 v1】。

估計式為什麼要有兩項（受限項 ＋ 局部項），見 `thermoforge/data/sampler.py` 的 docstring：
只用自由空間項的話，熱擴散長度大於板子時會高估功率一個量級。

## 切分

### 兩層，兩種身分

| 切分 | 內容 | 用途 | 可以看幾次 |
|---|---|---|---|
| `id-val`（5 fold OOF） | 3600 列 / 900 base layout | 調參、比較候選 | 無限次 |
| `pool-dev` | 1200 列 / 20 個候選池 | **主要 metric** | 無限次 |
| `ood-holdout` | 800 列 / 5 個 regime | 外推會不會崩 | **一次** |
| `pool-frozen` | 1200 列 / 20 個候選池 | 篩選能力的最終判定 | **一次** |

### GroupKFold，不是 KFold

同一個 base layout（幾何相同）配多組操作條件，產生 4 個高度相關的樣本。
隨機切分會把兄弟樣本拆到訓練與驗證兩邊，模型只要記住幾何就贏了。

這是本專案**唯一**的 leakage 管道——輸入端沒有「推論時取不到的欄位」，
時間方向也不存在。所以防線全部押在切分上，並且釘成機械化檢查：

- `check_no_group_leakage` 在生成時就跑，違反直接丟例外。
- `test_leakage_checker_catches_a_planted_violation` 種一個違規進去，
  確認它真的被擋。**沒看過紅燈的 gate 不算裝好**（繼承自 L0002）。

fold 大小：720 / 720 / 720 / 720 / 720【已確認：v1.manifest.json 的 `fold_counts`】。
均等不是美觀問題——fold 大小差太多時，fold 間的分數變異有一部分來自樣本數，
Gate 3 的「改善是否大於 fold noise」就判不準。

### OOD：一個 regime 只推一軸

| regime | 推出範圍的那一軸 | 改變的是什麼 |
|---|---|---|
| `ood_h_low` | h → 5–15 | 熱擴散長度變長，熱被困住 |
| `ood_h_high` | h → 80–150 | 熱擴散長度變短，核變窄 |
| `ood_ncomp` | 元件數 → 8–11 | 空間結構複雜度 |
| `ood_aspect` | 長寬比 → 1.60–2.40 | 邊界形狀 |
| `ood_power` | 熱點溫升 → 90–170 K | **正確答案已知**（算子對功率線性） |

一次只動一軸是刻意的：同時改三件事的話，模型崩掉之後無法歸因，
整個 OOD 實驗只剩「會崩」這一個沒有行動價值的結論。
`test_ood_regime_moves_exactly_one_axis_out_of_distribution` 把這條釘成測試，
並同時檢查該軸與 ID 區間**不相交**——重疊的話量到的是尾部表現，不是外推能力。

`ood_power` 的特殊地位：方程對功率線性，所以標準答案是「分數應該與 id 相同」。
在那裡崩掉代表模型沒學到線性，不代表這個外推本身難。它是一個**探針**，不是難度測試。

## 發現二：主要 metric 在一般資料集上是飽和的

原本打算直接在 id 的 3600 列上算篩選召回率。實測：

| 預測器 | recall@20/200 |
|---|---|
| `T_amb + P/(h·A)`（**完全不看佈局**） | **0.609 ± 0.088** |
| 隨機排序 | 0.108 ± 0.066 |
| 機會水準 k/pool | 0.100 |

【已確認：2026-09-07 在 v1 的 id 子集上實測】

也就是說那個指標有六成被一個沒看佈局的公式贏走。原因很直接：一般資料集裡
每一列的板子、功率、散熱條件都不同，所以候選之間的溫差主要來自「這塊板的功率密度多高」。
**在那個場景下做出來的任何模型比較都會誤導。**

修法是換評估場景，不是換指標。真實的設計迭代是板子、元件清單、功率預算、
散熱方案全部固定，只換佈局——所以候選池必須照那個樣子生成：

| 池內固定 | 池內變動 |
|---|---|
| 板長寬、kt、h、T_amb、元件尺寸、功率比例、總功率 | **元件位置，僅此而已** |

於是 P/(h·A) 在池內是常數，作弊的預測退化成隨機排序。修完的實測：

| 預測器 | 池內 recall@10/60 |
|---|---|
| `T_amb + P/(h·A)` | 0.170 ± 0.114 |
| 隨機排序 | 0.150 ± 0.107 |
| 機會水準 | 0.167 |

【已確認：2026-09-07 在 pools_v1 的 dev 半邊上實測】

池內不變量由 `build_pools` 在生成時逐池檢查，任一欄位不是常數就丟例外。

**池內熱點溫度的全距中位數 23.6 °C**【已確認：同上】——這就是「只換擺放位置」
能造成的溫差，也是這個工具存在的理由。
