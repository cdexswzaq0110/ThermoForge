# 決策型指標定案前，先寫一個「作弊 baseline」去打它——打得動就是指標壞了

## 觸發情境

主要 metric 不是誤差而是**決策品質**：篩選召回率、top-K 命中、排序準確度、
推薦的 slate 品質。任何形如「從一堆候選裡挑出最好的幾個」的指標都算。

## 領悟

指標可以在**完全沒有模型參與**的情況下就拿到大部分分數，而那件事從指標的定義上看不出來。

本專案的篩選召回率原本直接在一般資料集上算。實測【已確認：2026-09-07，
在 3600 列 id 資料上，k=20 / pool=200 / 200 次重抽】：

| 預測器 | recall |
|---|---|
| `T_amb + P/(h·A)`——**完全不看佈局**，只用能量守恆 | **0.609 ± 0.088** |
| 隨機排序 | 0.108 ± 0.066 |
| 機會水準 k/pool | 0.100 |

六成的分數與模型無關。任何在這個指標上做的模型比較，比的都是那六成的雜訊。

修好之後（候選池內板子、元件、功率、散熱條件全部固定，只換位置）：

| 預測器 | 池內 recall@10/60 |
|---|---|
| `T_amb + P/(h·A)` | 0.170 ± 0.114 |
| 隨機排序 | 0.150 ± 0.107 |
| 機會水準 | 0.167 |

## 為什麼會撞到

錯誤假設是：**指標的定義正確 ⇒ 指標有鑑別力。**

篩選召回率的定義完全正確——它量的就是「用預測排序取前 K 名，真實最優 K 名留住幾個」。
問題不在指標，在**候選池怎麼組成**。候選之間如果在某個與佈局無關的軸上差很多，
那個軸就會主導排序，而指標量到的是那個軸。

這是 metric 與 evaluation scenario 的分工被搞混：`se-ml-lifecycle` 講「metric 對齊」，
但 metric 對齊之後還有一層——**評估場景要對齊決策場景**。真實的設計迭代是
「同一塊板、同一組元件、只換位置」，一般資料集不是那個樣子。

同一個形狀在別的領域：推薦系統用混合了熱門與冷門商品的候選集算 NDCG，
熱門度就會贏走大部分分數；分類器在類別極不平衡的集合上算 accuracy 也是同一件事。

## 下次怎麼做

**決策型指標定案前，一律先跑兩個對照：**

1. **作弊 baseline**——刻意只用「模型本來不該需要的那個資訊」做預測。
   在這裡是能量守恆給的 P/(h·A)；在推薦是商品熱門度；在時序是上一期的值。
2. **隨機 baseline**——確認機會水準在哪。

**作弊 baseline 顯著贏過隨機 ⇒ 指標飽和，先修評估場景再談模型。**
判準是「作弊 baseline 拿到的分數，與隨機的差距，佔了真實模型能拿的分數多少」。

修的是**場景**不是指標：把候選池組成改到「只有要量的那個因素在變」。
改指標（例如加權、換公式）通常只是把問題藏起來。

修完之後把兩個對照留在文件裡（本專案在 `docs/03-data-contract.md`），
因為下一個人看到 0.85 的召回率時，第一個該問的就是「隨機是多少」。

## 失效條件

- 主要 metric 改成誤差型（MAE、RMSE）——那類指標沒有這個失效模式，
  但會有另一個（尺度混合）。
- 候選池的組成改由真實使用日誌決定而不是自己生成——那時要檢查的是
  日誌的選擇偏誤，不是這一則講的場景設計。
