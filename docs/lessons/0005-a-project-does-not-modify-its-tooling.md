# 專案 session 不改工具 repo——即使缺陷是在這個專案裡撞到的

## 觸發情境

在專案 A 裡用工具 B（共用的 harness、模板庫、內部框架、design system），
撞到一個**屬於 B 的**缺陷。修 A 修不掉，因為那些檔案不在 A 裡。

## 領悟

**「缺陷屬於上游」推不出「這一輪就去改上游」。** 這兩件事之間少了一步。

2026-09-07 開發 ThermoForge 時撞到 Serendipity 的
[L0003](0003-bootstrap-template-and-checker-disagree.md)。我的推理是：
這個 bug 修不進 ThermoForge（那些檔案不在這裡），所以只有「上游修」或
「不修，留給下一個專案再踩」兩個選項。於是在工具 repo 開了分支與 PR。

漏掉的那一步是**改動半徑**：

| | 改動半徑 |
|---|---|
| 改 ThermoForge | 一個專案 |
| 改 Serendipity 的 `templates/` 與 `bootstrap_check.sh` | **所有現在與未來的專案** |

第三個選項一直都在：**只留紀錄，不動工具。** 把修正寫成 inert 的 patch 放
`docs/upstream/`，等工具 repo 自己排一輪。

## 為什麼會撞到

兩個錯誤假設疊在一起。

**第一個：「修不進這裡」＝「所以要修那裡」。** 少了「或者現在不修」這個選項。
一個缺陷被完整記錄下來、附上驗證過的修正，**已經是完成的工作**——
套用它是另一個決定，屬於另一個 owner。

**第二個、也是更貴的一個：我用錯了問法。** 我把「要我在那個 repo 開分支修嗎」
夾在一份「還有兩件可以接著做的」收尾清單裡，使用者回「都做」。
形式上授權有，但**那是用專案收尾的語氣，換到了一個改動所有未來專案的許可**。

授權的品質取決於問法有沒有把改動半徑講出來。沒講，拿到的「好」就不是對那件事的「好」。
這一條與 `.claude/rules/dispatch.md` 第 4 條（GIL：一次只問一個決策，附主要代價）
是同一件事——我違反的是「附主要代價」那半句。

還有一個事後才看清楚的訊號：**那個修正對本專案根本不是必要的。**
ThermoForge 用表格寫 `CONTEXT.md`，早就 8/8 通過。
**「這件事不做，這一輪會不會不完整？」答案是「不會」的時候，它就不屬於這一輪。**

## 下次怎麼做

1. **預設：專案消費工具，不改工具。** 在專案裡撞到工具的缺陷 → 寫進
   `docs/lessons/`，需要保留可執行的修正就存 patch 到 `docs/upstream/`（inert）。
2. **要跨那條界線，單獨問一次**，而且問句裡要有改動半徑：
   「這個修正會影響所有未來用這套 harness 的專案，要現在在工具 repo 動它嗎？」
   ——不要夾在收尾清單裡。
3. **先問自己：不做這件事，這一輪會不會不完整？** 不會的話，它是另一輪的事。
4. 已經跨過去了 → 撤乾淨：關 PR、刪遠端分支、把工作副本切回原本的分支，
   並確認 `git log`／`ls-remote` 與當初 clone 時一致。**diff 先存成 patch 再刪**。

## 失效條件

- 使用者明確說「工具的修正直接在工具 repo 做」——那時這一則的預設就翻轉，
  但第 2 點（問句要帶改動半徑）仍然成立。
- 工具與專案在同一個 repo（monorepo）——半徑的差異還在，只是不再有「開哪個 repo 的分支」
  這個外顯訊號，要更小心。
